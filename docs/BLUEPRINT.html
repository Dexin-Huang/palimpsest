2The provenance stamp PROPOSED

Every JSON artifact the factory writes embeds this block under a provenance key. It is the same information logged to stage_runs — which is what makes factory.db rebuildable from the workspace alone (design rule §6.4), and what makes every page answer "who made you, with what, at what cost."

"provenance": {
  "station": "read",
  "station_version": "read/v1",
  "model": "gemini-3.1-pro-preview",
  "prompt_name": "read/la/diplomatic_json",
  "prompt_sha256": "e3b0c44298fc1c14…",
  "params": { "temperature": 0.1, "max_output_tokens": 32768, "media_resolution": "high" },
  "tokens_in": 1543,
  "tokens_out": 812,
  "cost_usd": 0.0101,
  "config_fingerprint": "9f2a4c1e8b3d5a70",   // hash(station_version+model+prompt+params)
  "input_fingerprint": "4b8e2f9a1c6d3e05",    // hash of upstream artifacts consumed
  "created_at": "2026-07-08T14:02:11+00:00"
}

Non-model stations (acquire, prepare, assemble_page) omit model/prompt_*/tokens/cost_usd; the fingerprints and station identity are always present.

5Page-line artifacts

Layout decision to confirm: the factory writes one file per page per kind — e.g. page_transcription/f001r.json — instead of today's single transcriptions.jsonl. Rationale: per-page atomic writes, per-page fingerprints, and per-page refresh are the whole point of the ledger; a shared JSONL makes every page write contend for one file and every fingerprint ambiguous. Anything downstream that wants a JSONL view can collate one cheaply.

5.1 page_image/ · page_image_clean/ PROPOSED

Files named <page_id>.jpg (e.g. page_0000.jpg — same as today). prepare writes a sibling <page_id>.json stamp per cleaned image recording the cleaning profile + provenance, so image artifacts are fingerprintable like everything else.

5.1b page_regions/<page_id>.json — polygon lassos + route CONFIRMED (as built)

Deterministic ink-density segmentation (dark-ink core test defeats show-through; watermark letterforms suppressed by height; blob density floor defeats dirt/foxing). Decides how the page is read: blank costs zero tokens; full_page is one call; segmented lifts each region onto a white square tile for its own bounded call.

{ "doc_id": "vat_pal_lat_1199", "page_id": "f001r",

6Manuscript-line artifacts CONFIRMED (as built, rule 8: one output file)

reconstruct consumes all page_assembled and writes one artifact, manuscript.json. The model only plans — sections, page joins, a reader's note; the continuous texts are assembled deterministically in code from the page artifacts, so the reconstruction is verbatim what the line produced and every cross-page decision is auditable.

7The book handoff PROPOSED

The factory's terminal product: a readable book — an EPUB you can put on a device, and a page in a hosted static library you can share. Both render from one intermediate, the book model, so a theme or format change never touches the pipeline. (Ariadne integration is deferred entirely — see open questions; nothing in the line targets it.)

7.1 book/book.json — the book model

Written by publish from the reconstruction artifacts + metadata. Pure content, zero presentation — the single source both renderers consume.

{ "doc_id": "vat_pal_lat_1199",
  "title": "Codice miscellaneo (medicina)",

  "language": { "original": "la", "translation": "en" },
  "date_range": "1350-1400",
  "readers_note": "A fourteenth-century medical compendium of therapeutic
                   recipes, collected from various authorities…",
  "chapters": [
    { "id": "ch03",
      "heading": "De febribus",
      "translation": "For fevers of the tertian kind, take …",
      "original": "Ad febres tertianas, accipe …",

    "transcribed_by": "gemini-3.1-pro-preview",
    "translated_by": "gemini-3.1-flash-lite-preview",
    "pipeline": [ { "station": "read", "station_version": "read/v1",
                    "prompt_sha256": "…", "pages": 110 }, … ],
    "cost_usd_total": 3.42,
    "produced_at": "2026-07-08T…" },
  "provenance": { …stamp§2… } }

Chapters carry both languages; presentation is the renderer's job. Default layouts: EPUB = translation chapters with the original as a per-chapter facing section; site reader = original/translation toggle.

7.2 book/<doc_id>.epub

EPUB 3. Spine: title page → reader's note → translation chapters (original text per chapter after the translation) → colophon. The colophon is deliberate: every book states what transcribed it, what translated it, from which shelfmark, at what cost — provenance is part of the product.

7.3 site/ — the hosted library

A static site built from every published book model — no backend, deployable to any static host (GitHub Pages works). Site build is a library-level derivation, not a per-item station: rebuild it any time from whatever book/book.json files exist.

site/
  index.html                  ← the shelf: every published book, by archive/date/language
  assets/…                    ← one theme (css), no frameworks
  vat_pal_lat_1199/
    index.html                ← the reader: chapters, original/translation toggle, colophon
    vat_pal_lat_1199.epub     ← download link (copied from book/)

9Recipe schema PROPOSED

name: latin_manuscript          # unique; items reference recipes by this name
language: la                    # source language; prompts resolve under it
line:
  page:                         # ordered; conductor validates consumes/produces chain
    - station: acquire
    - station: prepare
      profile: parchment_default
    - station: read
      model: ${PALIMPSEST_MODEL_VISION}     # ${VAR} pulls from factory config/env
      prompt: read/la/diplomatic_json
      params: { temperature: 0.1, media_resolution: high }
    - station: translate
      model: ${PALIMPSEST_MODEL_READING}
      prompt: translate/la/with_brief
      requires_jig: translation_brief       # conductor holds this station until the jig exists
    - station: assemble_page
  manuscript:
    - station: survey

    - station: reconstruct
      model: ${PALIMPSEST_MODEL_READING}
      prompt: reconstruct/boundary_repair
    - station: publish
      formats: [epub]                       # book.json is always written; site build reads it

10Open questions

  1. Page images in the book? Vatican scans carry "© Biblioteca Apostolica Vaticana ALL RIGHTS RESERVED" — our transcription + translation is our work, but redistributing the images is a rights question per archive. Default: books ship text only, with IIIF links back to the source images. Revisit per-archive.
  2. EPUB tooling. Default plan: ebooklib (pure Python, no external binary). Decide at Phase-3 build time.
  3. Hosting target. site/ is host-agnostic static HTML; GitHub Pages is the assumed first target. Confirm when the first book publishes.
  4. Alignment granularity. page_assembled.alignment is reserved but empty in v1. Sentence-level original↔translation alignment would enable side-by-side reading at finer grain than chapters — its own workstream.
  5. Opportunity-mode shapes. Prospect is committed; DreamCandidate and the dream_hunt recipe's stations are deliberately absent here — they get their own blueprint section when that phase approaches.
  6. Batch lane. The Gemini Batch API becomes an execution mode of the gateway, not a separate pipeline — per-page artifacts and stage_runs are unchanged. Deferred until read/translate volumes demand it.
  7. Ariadne integration — deferred entirely. Nothing in the line targets Ariadne. Ground truth (verified 2026-07-08): Ariadne v0.3 has no sidecar ingestion and forbids sidecar files; it ingests one clean markdown file via ariadne v3 ingest manifestation. When integration returns, manuscript/translation.md is already the right input shape — no factory change needed.
